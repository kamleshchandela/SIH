# Themis — Gap Analysis & Scope-of-Improvement Report

Companion to [PRD.md](PRD.md). Where the PRD explains what Themis is, this document audits what's missing, fragile, or overstated — based on reading the actual source (`themis/src/`, `themis_app/lib/`), the project's own `doc/` chapters (which are candid about several of these), and git history.

Document version: 1.0 · Generated 2026-09-08

---

## 1. Summary Verdict

The deterministic core — OCR pipeline, LMPC rule engine, REST API, PostgreSQL persistence, Flutter desktop client — is real, benchmarked, and non-trivial engineering. But it is a **hackathon-stage system**, not a deployable government product. The gaps below fall into three buckets:

1. **Documented-but-unbuilt** — features described at length in `doc/` with no corresponding code (the project itself is honest about most of these).
2. **Built-but-fragile** — code exists and runs, but has known correctness bugs, security shortcuts, or scaling limits.
3. **Absent entirely** — standard engineering hygiene (tests, CI, deployment, licensing) that isn't mentioned anywhere.

## 2. Documented-but-Unbuilt (Spec exists, code doesn't)

These are the project's own aspirational chapters — worth knowing so nobody accidentally claims them as shipped.

| Claimed capability | Where it's described | What's actually in the repo |
|---|---|---|
| **RAG / pgvector Legal Copilot** — statutory exemption lookup, auto-drafted show-cause notices, natural-language Q&A over inspection history | `doc/extra/RAG_ARCHITECTURE_AND_LEGAL_METROLOGY_COPILOT.md` (full architecture, prompts, example notice text) | No `pgvector`, no LLM client, no embedding code anywhere in `themis/src/`. Zero call sites. |
| **On-device mobile OCR (Android NNAPI, INT8 models running in the app itself)** | `doc/engine/10_MOBILE_EDGE_PERFORMANCE_QUANTIZATION_AND_HYBRID_CASCADE.md` | `themis_app/pubspec.yaml` has no ONNX/NNAPI/TFLite dependency. The Flutter app is a **thin client** that uploads images to the Rust server over HTTP — it does not run inference locally. `themis_app/android/` is an unmodified Flutter scaffold. |
| **Confidence-cascaded Gemini 1.5 Flash fallback** for low-confidence fields | Same doc, §6 | No Gemini/cloud-LLM client code in `themis/src/`. |
| **`ppocr_cls.onnx` (0°/180° line-flip classifier)** | Shipped as a model file in `themis/models/` | Doc 11 §2.3 explicitly confirms: "the model file exists... but has **zero call sites** — it remains unused by design." Dead weight in the repo (adds to clone size for no runtime benefit). |
| **Server-grade detector `ppocr_det_server.onnx` (109 MB)** | Referenced as the "automatically prioritized" default in `doc/engine/README.md` | Present in `.gitignore` (excluded from git — too large for GitHub). Anyone cloning the repo fresh does **not** get this file and silently falls back to the much weaker 2.4 MB model, with no warning surfaced anywhere in the CLI output described in the docs. |

**Improvement scope:** either build these, or relabel the corresponding `doc/` chapters as "Phase 2 roadmap" rather than present-tense engineering specs — right now a reader (or a judge who reads the docs before the demo) can reasonably conclude more is running than is.

## 3. Built-but-Fragile: Correctness Issues

These come straight from the project's own `doc/engine/11_...md` "Known remaining issues" section plus direct source inspection — i.e., the team already found these but has not fixed them:

1. **MRP price extraction picks the wrong number.** On the Oats sample, the engine reports `MRP 460` (grabbing the pack-weight number near the MRP anchor) instead of the actual `₹100.00`. Root cause: first-regex-capture instead of nearest-numeral-to-anchor scoring. This is the same bug class as the `55gms`/date-artifact issues — **whatever anchor-then-nearest-value logic fixed Net Quantity (`nutrition_penalty` ranking, §3 of doc 11) was never applied to MRP.**
2. **Consumer-care email gets permanently dropped when OCR splits at `@`.** `WECARE` + `eIN.NESTLECOM` (split across two bounding boxes) never gets stitched back into `WECARE@IN.NESTLECOM`, so a fully compliant product keeps showing a `ConsumerCare Warning`. No `@`-aware token-stitching exists.
3. **Non-deterministic OCR output on identical input.** Doc 11 records 168 vs. 201 tokens across repeated runs of the same Maggi image at the same 0.15 detection threshold — meaning **the same photo can flip between risk tiers on re-scan.** For a system whose entire pitch is "deterministic, court-admissible evidence" (doc `RAG_ARCHITECTURE...md` §5), run-to-run non-determinism is a direct contradiction of the core value proposition and the most serious open issue in the repo.
4. **The checked-in benchmark artifact is stale.** `batch_scan_results.json` (1.2 MB, sitting in the repo root) was generated by an older binary/scoring version, per doc 11 §6 item 4 — the doc explicitly warns "re-run before any demo or judge review." As of this audit it has not been re-run (file is unchanged since the fixes landed). **Anyone citing the "86% CRITICAL" headline number from this file is citing a number the team itself says is outdated.**
5. **Currency/unit OCR collisions remain unresolved in the shipped regex set.** Doc 09 documents `₹→R` collisions (`MRP ₹` → `"MRPR"`, failing the `\b` word-boundary regex) and terminal-suffix truncation (`500ml`→`500m`, which then gets flagged as an *illegal* unit rather than recognized as a truncated legal one). Doc 09 §4 proposes resilient regex replacements (`RE_MRP_RESILIENT`, `RE_NET_QTY_RESILIENT`, `RE_MFD_DATE_RESILIENT`) but a source check shows the current `rules.rs` was not confirmed to contain these — the fixes are written as a roadmap ("Optimization 5"), not confirmed as landed.
6. **Two-column layout interleaving is a documented open failure**, not yet solved by the "line-quantized" sort (`y/16` then `x`) that exists today — that sort fixes crash-safety (no more panics) but doc 09 §"Failure Mode 2" shows it still blends left/right columns into a broken reading-order string on multi-column labels (the SaveMore Dishwash case: 100% compliant product scored 12.5% Critical). The proposed fix (X-projection histogram column clustering, doc 09 Optimization 2) is unimplemented.
7. **Single wide-angle photos silently lose 75%+ of statutory text** (Yippee case: 50 tokens single-shot vs. 220 tokens multi-panel macro) with no in-product signal telling the person capturing the photo "this framing is inadequate" — the mitigation described (viewfinder AR guides, doc 10) exists only as a spec, not in `themis_app/lib/screens/`.

**Improvement scope:** prioritize #3 (determinism) and #4 (stale artifact) before anything else — they undermine the project's central legal/evidentiary claim and its own headline statistic, respectively. Then #1/#2 (anchor-based value extraction, `@`-aware stitching) since both have a known fix pattern already proven for Net Quantity.

## 4. Built-but-Fragile: Security & Production-Readiness

1. **Hardcoded fallback JWT secret.** `themis/src/auth/jwt.rs:15-19`:
   ```rust
   static JWT_SECRET: LazyLock<Vec<u8>> = LazyLock::new(|| {
       std::env::var("JWT_SECRET")
           .unwrap_or_else(|_| "themis-statutory-inspection-token-secret-2026".to_string())
           .into_bytes()
   });
   ```
   If `JWT_SECRET` is not set in the environment, the server silently signs every token with a **publicly-known, checked-into-git string**. Anyone who reads this file (or this report) can forge an `Admin`-role JWT for any deployment that forgot to set the env var. This is a real vulnerability if the binary is ever run outside a laptop demo.
2. **Hardcoded default credentials in source, not just docs.** `themis/src/api/routes.rs:502-509` compares plaintext against `"admin@themis2026"` / `"inspector@themis2026"` directly in code — no bcrypt/argon2 hashing, no user table, no way to change credentials except editing and recompiling. `doc/extra/ADVANCED_COMPLIANCE_AND_EVIDENCE_ENGINE.md` documents these as "Pre-Configured Credentials (Environment-Configurable)" but the code shows they are **not** environment-configurable — they're string literals.
3. **`CorsLayer::permissive()` + no rate limiting.** Every origin, header, and method is allowed (`main.rs:384`), with no visible rate-limiting middleware anywhere in `themis/src/`. Combined with a 100MB upload body limit, this is an open door for trivial resource-exhaustion (upload spam) against a CPU-bound OCR endpoint — fine for a local demo, not for anything internet-facing.
4. **No password hashing / no user management system.** There are exactly two accounts, both baked into the binary. There's no path from here to a real multi-inspector deployment (hundreds of DoCA field officers) without a rewrite of the auth layer.
5. **25 `.unwrap()`/`.expect()`/`panic!()` call sites** across `themis/src/api/routes.rs`, `themis/src/auth/jwt.rs`, and `themis/src/compliance/rules.rs` — any one of these, if hit by unexpected input (malformed multipart field, corrupt image header, unusual regex capture state) on a running Axum handler, brings down that worker thread/panics the request instead of returning a clean `4xx`/`5xx`. For a service meant to ingest untrusted images from field inspectors, this is a availability risk worth auditing file-by-file.
6. **No database migration tooling.** `db/repo.rs::init_db` runs raw `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX` statements on every startup instead of using `sqlx migrate` or similar. Fine at one-table scale; will not survive a schema change once there's production data to preserve.
7. **No Docker/Compose/deployment manifest anywhere in the repo.** The only Windows-specific guidance is `doc/extra/WINDOWS_DEPENDENCY_AND_SETUP_GUIDE.md` (a manual winget/MSVC/Rustup/PostgreSQL setup walkthrough). There's no containerized path to "government server deployment," despite that being an explicit design goal cited in `doc/engine/02_...md` ("Zero-Dependency Deployment... shipping a single, statically linked binary for government server deployments").
8. **Loose dependency pinning.** `Cargo.toml` specifies most crates by major version only (`tokio = "1"`, `axum = "0.8"`, `regex = "1"`, etc.) with `Cargo.lock` explicitly gitignored — meaning two different `cargo build` runs on two different days can legitimately pull different minor versions. For a system whose selling point is deterministic, reproducible, court-admissible output, an un-pinned, ungit-tracked lockfile is a reproducibility gap.

**Improvement scope, in priority order:** (a) require `JWT_SECRET` at startup — refuse to boot without it rather than silently falling back; (b) move credentials to a hashed user table, even a minimal one; (c) commit `Cargo.lock`; (d) add a `Dockerfile`; (e) sweep the 25 unwrap/panic sites in request-handling paths and convert to typed error responses; (f) add basic per-IP rate limiting (`tower-governor` or similar) before any public-facing deployment.

## 5. Testing & Quality Assurance Gaps

- **Backend:** 8 `#[test]` functions total, spread across `jwt.rs` (2), `quality.rs` (2), `rules.rs` (1), `export/mod.rs` (2), `pipeline.rs` (1) — in a 2,600+ line codebase (`rules.rs` alone is 939 lines) implementing 8 distinct statutory clauses plus OCR orchestration. There is **no integration test** that runs a known image through the full pipeline and asserts a known `ComplianceReport` output — the "before/after" verification described in doc 11 was done manually (`cargo build --release` + rerun CLI + eyeball the JSON), not captured as a regression test. This means every fix documented in doc 11 (orientation, net-quantity ranking, scoring) has **no automated guard against regressing again.**
- **Frontend:** `themis_app/test/widget_test.dart` is the default Flutter counter-app template test — it does not test any Themis-specific screen, widget, or API integration. Effectively **zero frontend test coverage.**
- **No CI configuration anywhere** (`.github/workflows/`, or any `.yml`/`.yaml` outside Flutter's own `pubspec.yaml`/`analysis_options.yaml`). Nothing runs `cargo test`, `cargo clippy`, or `flutter test` automatically on push — all verification in the changelog docs was manual, one-off, and done locally before commits.
- **No golden-image regression suite.** Given how much of doc 09 and doc 11 is "we found this exact failure on this exact photo, fixed it, verified by eyeballing the new JSON," the single highest-leverage QA investment here would be freezing the `dataset/mine/` + `dataset/real_products/` images as a fixture set with expected `ComplianceReport` snapshots, run in CI on every PR.

## 6. Product & Regulatory Scope Gaps

1. **No handling for non-English / vernacular label text.** LMPC declarations frequently appear in Hindi or regional languages on Indian retail packaging. The vocabulary (`en_dict.txt`, 96-character English-only dictionary) and recognition model (`en_ppocr_v4_rec.onnx`) are English-only. A large share of India's actual retail packaging (kirana-store staples, regional FMCG) is out of scope as shipped.
2. **No FSSAI license number check**, despite FSSAI licensing being adjacent/overlapping regulatory content that the dataset panels already contain (doc 03 mentions FSSAI licenses appearing on scanned panels) — the rule engine doesn't extract or validate it.
3. **Barcode/EAN-13 is present in `metadata.json` ground truth but not read from the image itself** — there's no barcode-decoding step in `themis/src/ocr/` (e.g., via a barcode library), so the system can't self-identify a SKU from a photo; it relies on manually supplied `product_name` or filename conventions. This limits the "search and retrieval facility for previously scanned products" (an explicit problem-statement requirement) to whatever text a human types in.
4. **E-commerce ingestion is explicitly punted, not solved.** `doc/todo/01_FRONTEND_HANDOFF_AND_ROADMAP.md` §1 argues (reasonably) against live scraping, but the problem statement (`sih26034.txt`) explicitly asks the system to check "product listings," and there is currently no implemented path — not even a manual CSV/catalog-bulk-import — for auditing an e-commerce catalog at scale. The system today is single-SKU-at-a-time (CLI batch mode aside, which is a local-directory feature, not a marketplace-integration feature).
5. **No admin-facing configuration UI.** Compounding fine amounts, risk-tier thresholds, and rule regex patterns are all Rust constants — an "Admin" JWT role exists (per doc & code) but nothing in the API or Flutter app actually lets an Admin *do* anything role-differentiated yet (no endpoint that only `RequireAdmin` gates besides possibly none found in `routes.rs` beyond the extractor itself — worth confirming there's real admin-only functionality, not just the auth scaffold).

## 7. What's Genuinely Strong (for balance)

To keep this report honest in both directions:
- The multi-panel SKU pooling concept and its documented empirical justification (doc 06, doc 08) is a legitimately sharp piece of domain reasoning — most naive hackathon entrants would not have caught the "single-panel fallacy."
- The Laplacian-blur quality gate protecting against wrongly penalizing manufacturers for bad camera work is a thoughtful, real touch of engineering care not found in a typical hackathon prototype.
- The engineering changelog discipline (`doc/engine/11...md`'s before/after tables, root-cause writeups, and explicitly recorded *failed* attempts) is unusually rigorous — most teams don't document their reverted mistakes. This is a genuine asset for iterating further, not just for judges.
- The rule engine's grounding in specific clause numbers with source PDFs checked into `dataset/rules/` is real regulatory diligence, not hand-waved "AI checks compliance" marketing.

## 8. Prioritized Fix List (if choosing where to spend the next sprint)

1. Fix OCR non-determinism (§3.3) — this is the one issue that contradicts the project's core "deterministic, court-admissible" pitch.
2. Re-run and refresh `batch_scan_results.json`, or delete it from the repo and regenerate on demand — a stale headline statistic is a self-inflicted credibility risk.
3. Require `JWT_SECRET` at boot; move the two hardcoded accounts to a hashed credential store (§4.1–4.2).
4. Commit `Cargo.lock`; add a minimal `Dockerfile` (§4.7–4.8).
5. Add an integration-test fixture suite over `dataset/mine/` + `dataset/real_products/` with snapshot assertions, wired into a basic GitHub Actions CI file (§5).
6. Port the MRP anchor-based extraction and `@`-aware email stitching fixes using the same pattern already proven for Net Quantity (§3.1–3.2).
7. Decide, explicitly, whether the RAG/mobile-edge chapters are near-term roadmap or long-term vision, and label them accordingly so the docs don't outrun the code.
